# 제품 화면 제작과 검수

사용자가 레퍼런스 추천·선택을 요청하면 실제 제품 레퍼런스 최소 5개를 추천하고, 사용자가 고른 방향과 채택할 요소를 확인한 뒤 구현한다. 에이전트는 새 시각 방향의 비교가 도움이 될 때 이 절차를 제안할 수 있다. 사용자가 선택 절차를 요청하거나 제안에 동의한 경우에는 선택을 기다린다. 일반 화면 구현 요청은 제품 목적·기존 브랜드·디자인 기준을 바탕으로 진행한다. 프로젝트의 디자인 기준(DESIGN.md, 프로젝트 지침)이 있으면 함께 따른다.

## 제품 레퍼런스를 화면으로 옮기기

새 화면을 만들거나 색·글꼴·배치를 의미 있게 바꿀 때 적용한다. 작은 문구·간격 수정은 기존 방향을 재사용한다.

1. 현재 제품의 실제 화면·디자인 기준과 사용자가 제공한 레퍼런스를 확인한다. 사용자가 레퍼런스 선택 절차를 요청했거나 에이전트의 제안에 동의했으면 실제 사이트·화면 사례 최소 5개를 원본 링크·추천 이유·채택할 요소와 함께 제시하고, 사용자가 주 레퍼런스와 요소를 고르면 구현한다. 그 외의 화면 작업은 제품 목적·기존 브랜드·현재 디자인 기준으로 진행한다.
2. 사용자 목적과 적용할 디자인 방향을 연결한다. 색의 역할, 글꼴·제목/본문 위계, 여백·정보 밀도, 배치·작은 화면 동작을 구현에 필요한 만큼 구체화한다. 해당 제품의 기존 디자인 토큰·컴포넌트를 우선 사용한다.
3. 정한 방향으로 요청 범위를 구현한다. 사용자가 레퍼런스를 골랐다면 채택한 요소를 제품의 실제 정보·행동에 맞게 옮긴다. 기존 브랜드·사용 흐름·접근성을 보존한다.
4. 실제 화면에서 정한 방향이 반영됐는지와 가독성·정보 우선순위·작은 화면·핵심 조작을 변경 범위에 맞게 확인한다. 레퍼런스를 채택했다면 적용한 요소와 제품에 맞춰 달리한 부분을 짧게 설명한다. 지침 적용과 실제 화면 검증을 구분한다.

## 구현과 검증 경계

- 기존 제품 결정과 디자인 기록은 설계 근거로 참고한다. 배포·게시·유료 호출·계정·데이터 변경은 해당 작업의 권한 경계를 따른다.
- 변경 대상의 코드와 실제 화면을 좁게 확인하고, 구현 후 변경을 증명하는 가장 작은 충분한 화면·동작 검증을 수행한다.
- 비교가 필요하면 실제 제품 캡처나 검증된 렌더로 같은 화면·viewport·데이터·상태를 비교한다. 레퍼런스 추천과 선택은 사용자가 요청하거나 제안에 동의한 절차에 적용한다. 채택된 방향의 작은 수정은 기존 기준으로 진행한다.
- frontend와 backend가 별도 Git이면 각 Git 루트와 연결된 제품 계약을 확인하고 필요한 범위만 구현·검증한다.
