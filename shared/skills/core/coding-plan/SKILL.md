# 요구사항·계획

사용자 목표를 관찰 가능한 결과로 적는다. 현재 repo 지침과 해당 코드부터 확인한다.
요구사항, 제외 범위, 영향받는 계약, 완료 조건, 검증 방법을 연결한다. 이미 답한 질문을 반복하지 않는다. 결과를 바꾸는 정보가 부족할 때만 질문하고 독립적인 조사는 계속한다. 질문에는 실제로 고를 수 있는 답 2~4개를 추천안부터 붙인다.
각 요구사항에 구현 위치와 확인할 시나리오를 붙인다. 미확정 가정은 사실과 구분한다. 계획을 작성한 것을 구현 완료로 보고하지 않는다.

## 목표 상태와 성공 기준

선택지를 비교하기 전에 결과를 쓰는 대상(사용자, 관리자, 결과를 읽는 프로그램)과 그들의 현재 작업 흐름, 그 흐름이 불편이나 손실 없이 이어지는 목표 상태, 현재와 목표의 차이와 각 차이가 중요한 이유를 적는다.
차이마다 `기준 | 작업 | 검증 시나리오` 표에 한 줄을 만들고, 끝에서 담당 작업이나 검증 시나리오가 빠진 차이가 있는지 점검한다. 빠진 차이는 작업으로 추가하고, 사용자가 제외한 차이는 이유와 함께 제외 범위에 적고, 근거가 부족한 차이는 미확인으로 남긴다.
범위는 사용자가 정한 대로 계획한다. MVP나 단계 분할은 사용자가 요청했을 때만 둔다. 목표 상태가 요청 문장보다 넓으면 그 점을 한 문장으로 알리고 전체 목표 상태를 계획한다.
작업 크기는 시간 대신 `XS`(작은 수정 하나), `S`(파일 하나와 테스트), `M`(한 모듈의 여러 파일), `L`(여러 모듈이나 계약 하나 변경), `XL`(여러 하위 시스템, 더 작게 나눔)로 적는다.

## 코드 변경 계획

- 각 단계는 결과를 확인할 수 있는 행동 하나로 쓴다. 테스트 이름과 검증 내용, 정확한 함수 서명과 파일, 실행 명령과 통과로 볼 출력 중 하나를 붙인다. `TBD`, `견고하게` 같은 선택을 남긴 단계는 빈칸으로 다룬다.
- 계획 본문이 구현할 코드보다 커지거나 함수 본문 위주이면 테스트 이름·검증 내용·서명으로 줄인다.
- `검토 초점` 절에 요구사항이 함의하지만 계획한 테스트가 다루지 않는 입력·실패를 가능성 높은 순서로 최대 5개 적고, 각각의 기대 동작과 테스트를 추가할 담당 작업을 붙인다. 찾지 못했으면 찾지 못했다고 적는다.

## 계획 수락

계획 수락은 사용자의 실제 답으로만 판정한다. 질문이 응답 없이 끝나거나 취소되면 계획은 수락 대기로 두고 인계·구현을 시작하지 않는다. 아이디어에 대한 동의는 그 아이디어만 승인한다. 이후의 계획·인계·변경은 각 단계에서 따로 수락받는다.
