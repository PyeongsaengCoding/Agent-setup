# 앱 제작 후보와 SDK 적용 조사

## 조사 순서

1. **대상과 결정 범위 확인.** 생소한 도구명은 사용자가 지정한 저장소·패키지와 대조한다. 후보 선택을 먼저 요청한 사용자는 비교표를 받은 뒤 제작 대상을 고른다. 도구 조사, 실제 분석 실행, 앱 구현, 스토어 제출의 상태를 각각 기록한다.
2. **기존 제품과 SDK부터 읽기.** SDK README, 실제 package 버전, 관련 기존 앱의 README를 확인한다. 적용 대상의 프로젝트 지침에서 계정·데이터 경계를 읽은 뒤 계정 연동이나 브라우저 작업을 시작한다. 같은 기능의 기존 앱이 있으면 확장과 신규 제작을 함께 비교한다. SDK 저장소 버전과 호스트가 포함한 AAR 버전을 따로 적는다. 문서의 버전 일치는 실제 산출물 적용 검증과 구분한다.
3. **시장 근거 확보.** 앱의 정확한 package ID·개발자와 일치하는 공식 스토어 자료, 운영사 공개 자료, 지역별 이용 데이터의 원출처를 찾는다. 각 수치에 `지역 / 플랫폼 / 지표 / 측정 시기 / 조회 시기 / 확인 방식`을 붙인다. 국내 언어로 표시된 스토어의 글로벌 누적 다운로드는 글로벌 지표로 표기한다. 대형 인접 서비스의 규모는 세부 후보 수요에 대한 간접 근거로 표시한다. 비교 가능한 국내 MAU를 확보하면 해당 기간으로 순위를 계산하고, 확보 범위가 부족하면 미확인 항목을 남긴다.
4. **선정 가능성이 높은 구현을 좁게 읽기.** 공식 저장소의 커밋, 실제 라이선스, README와 핵심 흐름의 모듈을 확인한다. 초기 비교에서는 후보별 핵심 모듈부터 읽고, 출력은 동작 요약·경로·커밋으로 제한한다. 원문 전체를 반복 출력하면 후보 비교에 필요한 근거가 묻힌다.
5. **SDK 결합과 수익 접점 비교.** 후보의 native Android, React Native, Flutter, Cordova, 웹 구조를 SDK의 실제 제공 브리지와 대응시킨다. 추가 브리지·서버·데이터 준비·권한 검사가 필요한 지점을 적는다. GPL/AGPL 참고 구현을 채택할 때는 수정 소스 제공과 SDK 결합 배포 조건을 확인할 항목으로 남긴다. 루트 라이선스 파일 하나의 조회 실패만으로 전체 배포 조건을 판정하면 다른 구성요소의 계약을 놓칠 수 있다.
6. **결정 자료 전달.** 표에는 `핵심 사용자 기능 / 지역 시장 근거 / 참고 구현·라이선스 / SDK 연결 작업 / 구매 접점 / 남은 검증`을 담는다. 추천 순위·수익 적합성·난도는 판단으로 표시하고 실제 매출은 구매·정산 보고에 근거한다. 채팅에는 추천과 짧은 비교표를, 상세 자료에는 고정 소스·출처·검증 경계를 둔다. 사용자가 선택할 다음 행동으로 마친다.

## GitHub API로 고정 소스 확인

아래 순서는 저장소 README·라이선스·핵심 모듈을 조회하는 데 사용할 수 있다. 요청에 준 식별자는 그대로 보존하고 API가 반환한 canonical 이름은 별도 필드로 기록한다.

```text
GET /repos/{owner}/{repo}
  -> full_name, default_branch
GET /repos/{owner}/{repo}/commits/{default_branch}
  -> sha
GET /repos/{owner}/{repo}/git/trees/{sha}?recursive=1
  -> 실제 README·LICENSE·핵심 모듈 경로
GET /repos/{owner}/{repo}/contents/{path}?ref={sha}
  -> encoding 확인 후 content 디코딩
```

- README를 읽어 제품의 핵심 흐름을 고른 뒤 해당 모듈을 읽는다. API 언어 통계와 라이선스 배지만으로 구조·재사용 조건을 확정하면 구성요소별 차이가 빠진다.
- 파일명을 트리에서 확인한다. 루트의 관례적인 파일 경로를 추측해 반복 조회하면 하위 패키지의 정본을 놓친다.
- 영구 자료에는 저장소 식별자, 커밋, 읽은 파일, 동작 요약과 오류·누락을 기록한다. 전체 타사 소스와 비밀값은 비교 자료에 복제하지 않는다.
- 분석 도구의 README가 특정 OS에서 검증됐다고 설명하면 그 범위와 현재 호스트의 실행 검증을 따로 기록한다. 문서 조회 성공을 로컬 도구 준비나 APK 분석 완료로 보고하면 실행 경계가 흐려진다.

## 제휴 수익화와 스토어 검토

후보의 독립적인 기능과 상품 구매 접점을 먼저 설계한 뒤 최신 스토어 정책과 제휴 조건을 확인한다. 사용자가 상품을 선택해 구매 버튼을 누르는 흐름과 SDK의 자동 백그라운드 URL 실행은 각각 검토한다. 사용자 동의·철회, 권한 취소, 데이터 수집 선언, 반복 콘텐츠 여부를 앱 선정 후의 검증 항목으로 남긴다. SDK를 넣었다는 사실만으로 정책 준수·제휴 정산·수익 발생을 판정하면 서로 다른 계약과 검증 단계를 섞게 된다.

여러 앱 후보의 핵심 흐름이 겹치면 통합 앱과 분리 앱을 비교한다. 브랜드·아이콘 교체 외에 각 앱이 제공할 독립적인 서비스 가치를 설명하고, 제출 전에 앱·계정·서명·공개 범위를 확정한다.
