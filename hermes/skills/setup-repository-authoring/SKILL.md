# Setup Repository Authoring

## When to use

Use when packaging an agent or developer environment into a reproducible installation guide. This skill covers packaging and verification, not a particular project's configuration.

## Procedure

1. Read the target repository's instructions and establish whether the request is review, editing, installation or publication. Do not expand that authority.
2. Inventory the actual applications, plugins, skills, dependencies and configuration. Distinguish installed, enabled, authenticated and exercised states. For a whole-document review, enumerate existing tracked and untracked documents with `git ls-files --cached --others --exclude-standard`, filter to actual files, and read every included document; directory matches and deleted paths do not count as coverage. Derive current totals from the manifest and reconcile installation tables, source notes and verification summaries.
3. Verify source provenance and redistribution rights. Keep project accounts, product decisions and report formats in their owning project, not in reusable skills. For overlap reviews, compare current clauses in both repositories and show their locations; different stated roles do not prove there is no duplication. Use exact-text searches to locate echoes, then review meaning and responsibility across entry documents, detailed guides, templates and installers; an empty identical-line intersection does not establish absence of semantic duplication. Bound the final conclusion to the documents and policy categories actually reviewed. Distinguish shared general principles, project-local rules and globally deployed policy. If the user rejects a duplicated principle, remove its echoes from entry documents, detailed guides, templates and installer dependencies, and update tests. Preserve concrete feature-specific setup checks. Removing a policy from distribution does not authorize changing an existing personal profile.
4. Write a short, goal-directed installation request. Keep exact commands and settings in their authoritative configuration; avoid repeating them across documents. Review AI-facing instructions for clear purpose, authority and completion criteria rather than humanizing their voice. Remove commentary that does not affect execution, but preserve exact model IDs, reasoning levels, fallback order and executable examples. Scope each prohibition or preservation rule to an explicit destination, operation or resource: excluding private data from Git publication must not prohibit authorized local profile imports, and preserving unrelated settings must not prohibit requested configuration changes. Replace vague defensive disclaimers with the allowed action and its concrete boundary; check sibling guides and distributed skills for contradictory blanket tool instructions. Scope every data exclusion to its destination: say personal data must not enter the Git repository or public artifacts, rather than implying that an authorized local profile import is forbidden. Check nearby preservation and security clauses against the requested migration; blanket bans on copying cookies or profiles can contradict a supported native import. State the allowed local transfer and the excluded publication separately, without promising that an importer preserves every data type or login. Keep personal experiments that are not installation targets out of the installation table.
5. Distinguish skills, plugins, project instructions and external tools. A skill document does not install its dependencies or authorize account access.
   - When consolidating several executors' setups (Codex, Claude Code, Hermes) into one repository, the goal is usually to PORT each portable feature into every other executor's native form, not merely to copy the sources side by side. Copying alone is an intermediate step; say so plainly if asked whether porting is done. Classify every feature as portable or executor-only, show that table, and confirm the porting scope before implementing. Details and the routing recipe: `references/cross-executor-porting.md`.
   - Write the user-facing docs you author in direct, positive statements of what applies where. Drop defensive disclaimers, "this is not X" contrasts and scope hedges about other projects the user did not raise; unrelated repositories need no mention.
6. Preserve existing profiles, credentials, user data and unrelated customizations. Preview changes, detect conflicts and provide a rollback before applying an authorized installation. If another session changes a shared file or an edit reports a sibling-write warning, re-read the file and its authoritative configuration before further edits; fuzzy matching can apply stale values successfully and undo a concurrent change. Reconcile against the newest source rather than restoring the earlier snapshot.
7. Verify first installation, repeated application and conflict handling in an isolated test target. Then verify the actual requested environment separately. Preserve dated verification records as historical evidence instead of replacing their counts with current totals; make the current summary explicit about what was rechecked. After document changes, run the repository's inventory/link checks, relevant tests and `git diff --check`; also confirm that deleting an installation-table row did not split the single Markdown table with a blank line.
8. Publish only when requested. Before answering whether everything is committed and pushed, run `git status --short`, `git diff --cached --stat`, `git rev-parse HEAD` and `git ls-remote origin refs/heads/<branch>`; distinguish published setup sources from untracked reports and verification records, because matching local and remote commits does not establish that every local file was included. Explain the purpose of leftover records when asked and distinguish archival evidence from installation inputs by checking installer or generator references, not folder names alone.
9. For an authorized archive commit, read the exact record set, validate JSON, inspect sensitive content and check repository visibility with `gh repo view --json visibility` before publication. Exclude credentials, conversations, browser data, personal memory and material outside the approved disclosure scope; private visibility does not make secrets safe to commit. Stage only the named files and run `git diff --cached --check`. If whitespace checks fail, fix only the reported formatting, re-stage and repeat the check before committing. Push the authorized branch, then compare local HEAD with the exact remote ref and check worktree status again. Report the commit, remote match and any remaining files concisely; do not imply archival records are required for setup unless the execution path actually consumes them.

## Completion

Report what changed, what actually worked and what remains unverified. Follow the target project's platform, routing, document and reporting decisions rather than defining them here.
