# Project Reference Adoption

Turn external articles, examples, tool announcements, and design references into concrete changes worth making in the user's actual projects. The deliverable is a project-specific recommendation or an authorized change, not a generic source summary.

## When to Use

- The user supplies links and asks which existing projects should adopt what.
- The user chooses where a reviewed method, reference source, or production tool belongs.
- An approved adoption needs to become a discoverable project or generator contract.

Do not use for general web summaries, standalone visual design, or installation-only requests without a project-adoption decision. This skill owns source-to-project comparison and scoped adoption; specialist design and tooling skills own their actual implementation.

## Procedure

1. **Identify the decision before expanding research.** Separate a question about the review process from a request to review sources, a request to adopt a method, and a request to install or operate a tool. Treat a quoted request followed by “can I ask this?” as prompt review, not authorization to execute it. For comparisons, identify both baselines and distinguish the generator, existing products, and personal executor instructions; do not widen a repository comparison to global configuration without a reason tied to the request. Briefly answer an explicit process question, then continue the source review already requested. Incorporate mid-turn corrections into the active scope; do not keep executing the superseded interpretation.
2. **Establish the source coverage.** Read the supplied material and necessary continuations, distinguishing author claims from observations. Use the current configured browser workflow for live navigation and authenticated pages. If the selected account is not specified, resolve it before using authenticated state. When a text extractor fails, try an appropriate permitted alternative rather than infer content from the title. Keep media coverage separate from caption coverage. For social carousels, preserve the requested card index, verify that card visually, then inspect the surrounding cards needed for the conclusion; distinguish static-card coverage, representative video frames, full playback, and audio. Use the carousel recipe in [design foundations](references/design-foundations.md) when accessibility snapshots omit image text. For multipart social posts, read the author's continuation replies and separate them from algorithmically recommended posts; a page title behind a login overlay covers only the title, not the whole thread.
3. **Find the correct owner of the proposed change.** Resolve unfamiliar names and acronyms from the project's terminology and prior decisions before researching a similarly named external tool; a matching name does not establish its role in this project. Read the candidate project's current contract and search its relevant implementation. For new-product defaults, inspect the bootstrap/generator rather than automatically editing a common agent environment. For an operational tool, inspect the production project's current workflow. A new repository and a previously generated repository adding its first UI are different application scopes: generator changes do not automatically update the latter.
4. **Compare behaviors, not tool names.** Treat the user's failing example as an acceptance scenario, not a domain restriction, when they are asking for a general product capability. State that capability before selecting a tool. Separate semantic judgment, information acquisition, action execution, and server-enforced permissions; a decision model is not a browser engine or an authority grant. State what exists now, what would change, which actual problem that addresses, and which existing rules remain. When the user asks whether proposed items duplicate existing capabilities, inspect both the owning project rules and the relevant installed skills before deciding. Map every requested item to existing coverage, its missing behavior, and the proposed action; general prose cleanup, language-specific review, deterministic code checks, and assumption reassessment can overlap in purpose while covering different mechanisms. Reuse covered behavior and integrate only the missing criteria into the existing owner, because installing another named skill can duplicate work without adding capability. Evaluate conditional adoption against that comparison and preserve the user's condition; account for every requested item in the result. If the method is already implemented, distinguish that from adopting additional sources or choosing a preferred production tool. For reference services, evaluate adding the public source separately from connecting its authenticated MCP: a useful gallery can expand discovery while OAuth, a paid plan, or external generation introduces a separate decision. Verify the service's current scope and access conditions in its own documentation; social cards can narrow a broad service to one feature or show older allowances. Do not keep calling an explicitly selected tool a mere reference candidate. Conversely, do not claim installation or working integration from a written preference.
5. **Give a usable recommendation.** Before calling an implementation recommendation reviewed, trace its actual input, storage owner, update/projection path, and downstream consumer; identify missing links and distinguish source review from exercised behavior. If the user challenges a feature's value, compare the existing accepted purpose with the observed benefit instead of inventing adjacent alerts, discovery features, or documentation to justify keeping it. Lead with the target project and the exact behavior to adopt, adapt, retain, or omit. Include the smallest sufficient application test and only material cost, account, or data changes. Use concise Korean when the user is speaking Korean. Explain the applied outcome rather than making the user choose from an abstract workflow taxonomy.
6. **Apply only the decided layer.** After approval, update the existing owning contract and preserve its working discovery path. When the user supplies a recording to explain an already accepted direction, transcribe and read the relevant passages before replacing an earlier interpretation. Attribute approval to the user's explicit instruction and its exact scope; use the recording as interpretive evidence with timestamp references, and keep private call text outside the repository. Preserve the distinction between a feature's accepted meaning, the broader product purpose, and an unaccepted implementation proposal, because a supporting conversation cannot grant the missing scope. Preserve independently approved layout and authority rules until their change is explicitly decided, because agreement on product meaning does not select pagination, default collapse or a renderer. When simplifying instructions, read every scoped document first; delete repeated explanations, source-origin labels, rigid taste defaults, and unnecessary process gates while keeping product goals, approved decisions, security/data/permission boundaries, and actual verification outcomes. Prefer one owning rule with short links over restating the whole workflow at each entry point. For a content transfer or cleanup, move the requested substance and remove the old source; do not turn organization into new templates, fixed file layouts, compulsory read chains or cross-repository ownership notices. Add a discovery change only when the accepted behavior would otherwise be inaccessible, not as a default deliverable. For a generator, verify its existing procedure actually carries the criterion into the generated project; for a production project, use the existing workflow entry point. When an integration becomes a new-app default, read the SDK and service contracts first and distinguish each supported platform's path. Update the owning integration contract, creation-time document selection, and generated product's contract pointer while preserving user participation and operational approval boundaries; a default dependency does not authorize activating devices or creating production resources. When one request authorizes a concrete edit and asks for discussion of another rule's location, perform the edit and leave the placement recommendation pending. Resolve a later proceed instruction against the most recently proposed action: continue a requested comparison as a comparison, and carry an accepted implementation through code and verification instead of returning another design-only report. State the active execution and remaining acceptance boundary plainly when the user asks whether work has progressed. Prefer goal-and-direction guidance over prescribing every document implementation so the model can adapt to project context. Record decisions separately from observed execution. Consult the topical notes below for design foundations or editing-tool changes.
7. **Verify the changed contract.** Exercise relevant generation checks when changing templates; validate local links, section anchors, discovery paths, and duplicate reference entries. Preserve untouched instruction regions and unrelated work. Select the project's supported runtime for tests and report any skipped platform checks without rewriting unrelated code merely to accommodate the host's default interpreter. Measure reduction against a named baseline, distinguishing the committed predecessor from the session's pre-edit draft; report character or byte counts as such, not as model token savings. Do not treat document checks as evidence of UI quality or successful media production.
8. **Report the final state briefly.** Name the two or three practical changes, what actually passed, and the remaining execution boundary. Say explicitly when only policy has changed and the app, account connection, first UI, or first export has not been exercised.

## Standing preferences

- For quality benchmarking of an existing product, first separate shared experience criteria from the product's distinctive capability. Use competitors to learn answer readability, progress visibility, evidence inspection, recovery, and operational reliability; judge the product's own decision workflow against its user goal, supplied constraints, evidence, coherent comparison, and actionable conclusion. Investment or reputation motivates research; observed behavior supplies the quality verdict.
- When the user wants lessons from competitors and has no accounts or interest in joining, use official public material, demos, and primary engineering references. Keep authenticated parity tests outside that scope and state which behavior was observed versus described by a source.
- Rank recommendations by the requested user-visible improvement. Keep security hardening and verification documentation in their own categories; propose them when an observed failure or approved scope justifies them. Explain a critical-flow checklist as a way to retain regression coverage, and ground quality improvements in changed behavior with an exercised user flow.
- For requests to compare open-source implementations before discussing direction, read pinned implementation code and the product's current contracts first, then present the existing capability, reusable pattern, remaining gap, and recommendation. Keep purpose discussion and accepted implementation separate; a library demonstration establishes its observed behavior, while the user's desired outcome supplies the adoption criterion.
- Separate automatic knowledge use from user-facing knowledge visualization. Establish the user's stated purpose before recommending graph interactions: exploring records, seeing how the system understands the user, and optionally correcting that understanding are different tasks. Keep routine connection maintenance automatic; asking users to audit every inferred edge shifts the product's work onto them. For an accepted understanding-snapshot purpose, make relationship meaning, source versus inference, and voluntary edits legible, then verify that a scoped edit changes the next relevant answer or decision. Keep claimed trust or quality gains as hypotheses until observed, while preserving the user's confirmed purpose as a decision.
- Assign adoption rules by responsibility after comparing the current clauses: put new-product defaults, reference-source lists, and design-research cost eligibility in the product generator; keep general implementation/verification methods and executor tooling in the agent-setup skills; keep actual tokens, integrations, and observed state in the generated product. Extend the existing owner with only the missing criterion, because copying the same workflow into generator and agent setup creates competing contracts.
- Apply an explicit free-only constraint before ranking adoption candidates. Separate free public reference browsing from paid MCP access, and exclude paid subscriptions and card-required auto-renewing trials from that scope. Switch to another public example at a paywall. Treat a limited free generation tier as optional when it adds an account, external data storage, or quota handling; an allowance alone does not justify adoption. Keep the cost constraint scoped to the requested tools or research rather than changing unrelated model or cloud policies.
- For multi-project instruction adoption, inventory each repository and its instruction owners separately, then read its instructions and connected contracts rather than every unrelated document. Apply only relevant criteria to each product, preserve existing design/data/account/approval decisions, keep personal and company boundaries separate, and retain each project's own canonical documents. Do not rerun new-repository bootstrapping or create an ongoing dependency on the generator.
- Keep approved Humanizer and AI-slop preparation discoverable when shortening adoption guidance. Distinguish prose review from code cleanup: instruction/document work does not authorize product-code refactoring. Preserve installed or customized skills, prepare compatible skills for the actual executor when authorized, and verify loading rather than importing one executor's tooling into another executor.
- When explaining where a rule lives, read the owning project document and distinguish that portable criterion from the executor-specific tool example and actual installation. Do not imply that a Humanizer or AI-slop criterion moved into a particular executor just because its document mentions that executor's skill.
- Create a product's visual criteria while building its first UI, not as a lengthy preliminary document or a repeated approval gate. Carry the user's actual reference recommendation/adoption requirement through the owning project contract instead of replacing it with fixed visual defaults or an optional source list. Use the generator's design document as the owner of the actual reference-site list and recommendation criterion; name sites directly rather than referring agents to the post where they were discovered. Keep Land-book, Mobbin, and Siteinspire in the same pool. Do not repeat the list or detailed criteria across README, creation procedure, and generated AGENTS. Pretendard remains a Korean starting font candidate.
- Before UI work whose visual direction is undecided, read the product's current design-reference rule and the generator contract it was built from; a summarized plan line can omit the actual selection and implementation conditions. Apply the contract's required reference count and present source links, observed screens, recommendation reasons, reusable elements, and coverage limits. Honor the user's selected references. When implementation is authorized and the current contract permits proceeding without a selection, choose for the product's purpose and existing brand, record the reason, and implement. Prepare concept combinations or a separate comparison package when requested or required by that contract. Preserve the current product rules within the approved change scope. Details: [design foundations](references/design-foundations.md).
- Keep the agent responsible for setup, implementation, editing, and verification within the authorized request; do not turn adoption into a list of manual production chores for the user.
- Keep recommendations, user choices, rule changes, installation, integration, produced artifacts, and observed quality distinct in both records and final answers.
- Design for the user's general outcome when they ask for capability parity; use accommodation, statistics, or shopping examples to test that outcome rather than turning each into a separate product feature.
- Place a newly adopted judgment model only at justified, narrow decision points in the existing flow; do not replace the main reasoning model, add a mandatory preflight to every action, or rebuild the agent hierarchy without a demonstrated need.

## Evidence pitfalls

- Attribute only tool operations that actually returned source content; a plausible URL or an attempted extraction is not a successful source read.
- Correct an unsupported evidence statement in place before carrying it into an adoption history; later policy approval does not validate earlier research claims.
- Preserve the distinction between a chosen reference and copied implementation; importing code, dependencies, brand assets, or accounts introduces a different adoption boundary.
