# Design Foundations

Use this note when adopting reference-driven UI design into a new-product workflow.

1. Inspect the generator's design contract, creation procedure, and generated agent instructions before adding a new file convention. Establish whether the project means a readable visual guide or a particular machine-readable DESIGN.md schema; the filename alone does not establish a schema or justify extra CLI dependencies.
2. Select references by the product's surface and user task. Read the generator's current reference-site list and recommendation criterion from its design contract. Present distinct actual design references with source links, product fit, reusable elements, and limits; apply the required minimum when that contract calls for one. A list of gallery names or five AI-generated concepts does not satisfy that requirement. Separate required reference recommendation/adoption from optional new concept comparison and approval gates. Keep the shortlist searchable and deduplicated; do not require visiting or installing every source. If fewer than five can be verified after alternate retrieval, report the unmet criterion instead of inventing examples.
3. Translate useful elements into the product's own root DESIGN.md: semantic color roles, typography, spacing and density, responsive layout, components and states, and purposeful motion. Treat external DESIGN.md files as inputs to interpret, not contracts to copy wholesale.
4. Give visual values one owner. Connect DESIGN.md to the actual CSS/token/theme implementation; keep decision rationale and reference provenance in the existing decision record. Point between the two rather than duplicating palettes, font scales, and spacing values.
5. Connect the generated AGENTS and documentation index to the product's DESIGN.md. UI-free products defer this until their first UI. Existing products keep their current canonical design contract unless migration is explicitly in scope.
6. Treat Pretendard as the Korean starting font candidate rather than overriding the adopted design reference. Choose typography for the product, language, platform, performance, and readability; record the choice. Keep the correct family, weights, license notices, and a system fallback, and verify actual loading and Korean wrapping instead of treating a CSS declaration as proof.
7. Implement the first screen and verify real desktop/mobile layouts, reading hierarchy, states, and key actions. Write formal-schema exports only when the project's consumer needs them; unconsumed token files create a second source of truth without improving the screen.

Policy checks prove the generator knows what to create. Only a generated product with a rendered, exercised UI proves the resulting experience works.

## Reference recommendation package for user selection

- Research order: choose sources by the product's operator tasks (e.g. for payout/settlement consoles: state queues, approval steps, unknown/needs-review lists, event timelines, ID search for reconciliation), then mix product demos, official help/docs screenshots, and gallery entries (Mobbin, Refero) from the contract's site pool. Non-domain products are valid when their pattern fits a task (an issue tracker's grouped review queue).
- Capture real pixels: drive public demos in the browser; for docs/help pages, list page `img` elements with natural size, keep only large screenshots, download them through the browser's cookie-bearing fetch, and validate the bytes as an image before saving under project-records. Visually inspect each image before describing it.
- Exclude a candidate whose captured screen is only loading placeholders or whose content cannot be seen; replace it rather than counting it.
- When a reference-selection package is requested, deliver a recommendation report in reports/ (table: number, linked reference, observed screen, why it fits, elements to adopt), a contact-sheet comparison image, and a coverage section separating live demo vs official-doc image vs gallery capture and what was not verified (execution, permissions, responsive). Add named combinations when requested or required by the current contract. Record artifacts and the actual selection state in project-records; update the decision doc only within the authorized scope. Copy structure and state patterns only, never logos, brand colors, or illustrations.
- Ask for a selection when the user requested a selection-stage deliverable or the product contract requires one. For an authorized implementation whose contract permits an agent-selected direction, proceed from product purpose and existing brand and record the chosen elements; a missing selection alone does not add an approval gate.
- Contact sheets downscale every panel until text is unreadable; deliver the full-size captures alongside it and say plainly that judgments come from static screens (only a live demo shows transitions, permissions, responsiveness).

## When the user has chosen a design system (e.g. shadcn/ui)

- References then supply screen structure, workflow, and state presentation; the chosen system supplies components and tokens. Record that split and the still-open theme choices (base color, radius, font) in the decision doc.
- For each reference, state its underlying design system only with a cited source (e.g. an architecture doc naming a shadcn-based UI package); otherwise mark it not verified — never infer the system from looks.
- Capture the system's own official blocks/examples (for shadcn: `ui.shadcn.com/view/new-york-v4/dashboard-01`, `ui.shadcn.com/examples/tasks`) as a baseline, and add a table mapping each adopted reference element to concrete system components (Tabs+Badge, faceted filter, Sheet detail, Collapsible groups, Command, Card/Chart, Sidebar).
- shadcn tooling, distinguish the two official pieces: the agent skill (`npx skills add shadcn-ui/ui@shadcn`; component add/compose/styling, no lint) and `@shadcn/lint` (an ESLint/Oxlint plugin, not a skill; needs Tailwind v4; rules no-restyle, no-raw-colors, no-arbitrary-values, no-inline-styles, no-unknown-classes, require-static-classes). Its official SETUP.md only registers the plugin and enables no rules, so rule selection is a separate decision. Install lint with the frontend project, not before one exists.
- When asked whether a skill for some tool exists, search every installed executor's local skill root (for example `~/.agents/skills`, `~/.claude/skills`, Codex plugins) and then the vendor's GitHub/npm (read README/SETUP via raw.githubusercontent and the GitHub/npm APIs when page extraction is unavailable); report whether the thing is a skill, a package, or both before offering to install.

## Source coverage and account-bound reading

### Social-carousel reading

1. Preserve semantic URL parameters such as `img_index`; remove only tracking parameters. Open the requested position in the approved browser profile and take a snapshot scoped to the post where possible, so unrelated comments and recommendations do not dominate the source read.
2. Capture the requested card with `page.screenshot({path:'./artifacts/card.png'})` and inspect its pixels. Image text can be absent from snapshots and alt attributes, so caption-only extraction leaves the card's actual prompt or claim unverified.
3. For context, navigate to the first card and use the observed Next control in a bounded loop. Capture each position, refresh the snapshot after each click, and stop at the observed final position. Verify visible card numbers or distinct screenshot content: `No changes detected` in a snapshot diff can accompany a real image change.
4. Build a contact sheet from the full screenshots with a local image tool, using the observed card rectangle and screenshot pixel scale. Treat the sheet as navigation; inspect individual crops at legible resolution before interpreting small text. Reuse the loaded Python image-processing runtime where available instead of assuming the shell's default interpreter has the same packages.
5. Detect mixed-media cards from the observed player controls or `main video` elements. Report representative frames separately from full playback and audio coverage; a complete set of card screenshots establishes the cards' visible text, while animation and sound need their own observation.
6. Follow official service addresses actually shown in the cards or linked from their official sites, then verify capabilities, authentication, plan requirements, trial renewal, and external storage only as needed for the recommendation. Keep DM-gated supplementary material unverified unless receiving it is authorized; a comment keyword would create an external interaction.

- Write adopted sites directly into the owning design contract by name and link. Do not use labels such as “sites introduced in a social post,” source-origin columns, or supplementary tiers as operational guidance: they force future agents to reconstruct a list instead of using it. Keep author attribution and multi-part source evidence in research records when needed, separate from the site's eligibility for design discovery.
- When a public source is login-gated and the user supplies an account, resolve the exact imported Aside profile before reading. Match the user-supplied email through source-profile metadata when available; an Aside CLI account is not the website account. Prefer the existing session, do not switch unrelated accounts, and do not claim source coverage from only the page title. Read the author's continuations, not unrelated commenters, and keep account identifiers out of committed source-evidence artifacts.
