# Persistent-memory lifecycle invariants

Use this recipe when selection works but later deletion, correction, effective-time changes or replay can change what a consumer sees. Keep the model transport synthetic for lifecycle probes and reuse unaffected actual-model semantic evidence; lifecycle fixes alone do not require another paid classification run.

## Order of work

1. Locate the saved user statement, selection receipt, canonical item/event/settings transaction, deletion markers and every consumer validator. Trace consumers beyond initial compilation to model-reuse release checks and frozen decision validation.
2. Reproduce one failing lifecycle through the real worker and reader. Introduce one controlled change at a time and run the same command after the fix. Use the project's resolved interpreter with `-m pytest -q -p no:cacheprovider <focused-test-file>`.
3. Fix the authority or write boundary responsible for the failure. Reuse deletion suppression and owner-edit contracts before introducing another representation or classifier.
4. Expand to adjacent readers and atomic replay probes. Keep the source timestamps and reader clock independently controlled, so admission readiness and effective-time assertions test their intended boundaries.
5. Run the integrated focused module set against the final code, then `-m ruff check <changed-code-paths>`, `git diff --check` and the repository's architecture command. Preserve each exit status separately; a later successful command can hide an earlier nonzero result in a shell command chain.
6. Record exact module names alongside totals and keep child-reported checks separate from parent-observed execution. Re-review only changed lifecycle paths and previous defect scenarios, because an unchanged semantic or source-reference contract can reuse its earlier evidence.

## Deletion and owner correction

- Save a statement, delete it through the canonical owner command, then submit the identical quotation inside a mixed request under a changed model key and changed purpose. Assert zero new canonical items and no next-answer or explicit-decision use.
- Check each selected quotation against suppression independently of the complete input. A mixed request changes the whole-message fingerprint while retaining deleted content.
- Edit an automatically selected memory through the supported owner command. Assert the edited text remains usable on its intended reader and stale model-selection/effective-value proof is cleared.
- Verify scoped owner conditions through explicit selection rather than widening the ordinary answer reader. A correction must preserve the application's existing consent and use contract.

## Scheduled replacement representation

Retain the earlier value with its own source evidence, scope, validity and expiration. Bind retained value snapshots and the new canonical value to the same atomic recording event. Project the applicable value under the current canonical identity/revision; validate the projected value against its original source and selection proof.

Keep the future replacement in the model's existing-memory context even while current-use readers serve the prior value. Reject an add collision both during proposal admission and immediately before the canonical write, because a hidden or concurrently changed pending item can evade the first check.

Exercise these boundaries:

| Boundary | Required observation |
|---|---|
| Before replacement start | Earlier value is available while its own lifetime permits use. |
| Exact inclusive start | Replacement becomes applicable in answer and explicit decision readers. |
| Exact exclusive end | Replacement is excluded; expiration does not revive an older value. |
| Frozen earlier decision | Original cutoff and value remain intact under the existing historical-use contract. |
| Capsule model reuse crossing start | Old compiled value is rejected or recompiled; a historical-read approval cannot authorize new model use. |
| Source altered between validation passes | Release-fence validation rejects the stale proof before reuse. |
| Owner edit, item delete, clear or parent retirement | Current control wins over retained snapshots and pending selections. |
| Multiple scheduled replacements and cold reopen | Applicable values and current identity/revision survive reopening without process-local state. |
| Retention overflow | Preserve still-needed values and defer the new write; never truncate an applicable version merely to meet a bound. |

Declare the actual retention bound and overflow behavior. Prune completed intervals only after proving they are unnecessary for every supported current and historical consumer; otherwise retain or defer. Keep recovery of already incomplete history as a separate verified migration scope.

## Atomicity and dependency checks

Fail the owner transaction before writes and assert item, recording event, settings and usage remain unchanged. Retry from the durable selection result and count zero additional provider calls. Reopen a fresh store from saved documents and repeat reader validation.

Place shared pure parsing or policy helpers below both recording and suppression. Preserve supported caller imports when relocating a helper, then rerun behavioral and architecture checks; successful Python import and Ruff alone do not establish an acyclic dependency graph.

Report isolated-store, synthetic-transport, actual-model, authenticated UI and deployment evidence by their observed coverage. A passing lifecycle probe proves its exercised backend boundary; account-level answer relevance and map rendering still need the corresponding user flow.
