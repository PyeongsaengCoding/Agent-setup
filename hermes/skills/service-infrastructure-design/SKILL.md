# Service infrastructure design

Design from actual product execution and measured constraints, not a preferred hosting product. Use for current-to-proposed architecture, whole-system costs, communication paths, observability and scaling decisions. Complement API-contract and infrastructure-as-code skills rather than replacing them.

## When to Use

Load for service-infrastructure redesigns requiring a concrete existing-versus-added comparison, evidence-backed scaling, complete cost accounting or communication-path analysis. Do not substitute this for a narrowly scoped endpoint fix or an already-defined infrastructure apply.

## Procedure

1. **Establish the product scope, then trace the implementation and its consumers.** For a provider replacement discussed inside a product workspace, search that product's source and design documents for the incumbent and candidate before inspecting personal agent configuration. State whether the incumbent is proposed, implemented or deployed; the answer determines whether this is adoption or migration. Keep recommendations anchored to the product backend and deployment boundary, because a personal MCP installation does not connect the product's user flow. When the person names a product setting, inspect that product's configuration and transmitted request first; leave the personal agent's settings unchanged. Preserve the currently agreed reasoning effort while comparing architecture, and reopen that choice only when the person requests it. Follow request entry points through application calls, worker selection and storage/provider boundaries. Inspect direct streaming and background execution separately, including the query that admits retries. Locate actual claim/CAS, checkpoints, fairness, source readers and usage receipts before declaring them new work. Verify who calls each helper and which identity arguments reach it; a durable state helper with no consumer, a retrying turn excluded by worker selection, or a tool callback without the provider call ID leaves the execution disconnected. Keep unknown started provider/tool results fail-closed and design a separately typed, reconcilable awaiting state for durable work.
2. **Write the change table first.** Classify capabilities as existing, extended, new or unverified. Explain the user-visible behavior each change adds. Preserve working ownership, authorization and retained-data contracts unless a demonstrated requirement calls for replacement. For a production delivery goal, trace the default API and worker composition, reusable host transport, actual external-target support, and deploy packaging before extending the QA harness. Order missing production connections as implementation slices with explicit acceptance checks; a harness-injected callback or one-shot parent descriptor can prove a trial while leaving unattended product execution disconnected.
3. **Separate evidence from operations and qualify readers before producers.** Explain answer evidence, execution state and operational logs. Trace each new source kind through citation admission, original-body reading, model-input freeze/replay, quality-stage selection, history reuse and saved-answer reopening before enabling its producer. An unknown source kind can silently fall through to an unbound excerpt path. Reuse current authorization and retention contracts; distinguish live new-use authority from saved-history read rights and execution deadlines. Check Workspace membership separately from owner/conversation lifecycle. Bind requested and applied conditions, observation time, scope and immutable source identity; a URL alone cannot identify a dynamic result. Keep bulky artifacts outside hot state documents and source bodies outside logs.
4. **Audit measurement coverage before sizing.** Inspect live server/client spans, role attribution, accounting receipts, completeness signals and dependency timings separately. Trace accounting admission through actual saved-state eligibility, claim and provider dispatch; exercise no-op replay and persistence failures before treating a ledger as reliable. Follow the bounded-accounting verification recipe in `references/measurement-and-capacity.md`. Keep repository support distinct from verified deployed collection; scope absent data to the resource queried.
5. **Map every communication path.** Include user-to-frontend/API, state/queue/artifact storage, external search/models/sites, browser-to-trusted execution and telemetry export where applicable. Specify measurement origin, representative payload, connection reuse, cold/warm state, samples and concurrency. Separate queue, admission, pool, lock, provider and rendering waits from transport. Classify each timing value as a configured timeout ceiling, a measured duration, a reserved margin or a demonstrated lower bound before comparing budgets; a startup timeout cannot establish minimum startup latency. Trace when each deadline starts and whether cleanup occupies the same serialized slot. Follow the lifecycle-budget decision recipe in `references/measurement-and-capacity.md` when choosing synchronous, prepared or asynchronous execution.
6. **Diagnose before expanding.** Connect backlog and latency to a constrained resource or dependency. Record evidence, competing explanations, cost delta, expected improvement and rollback. More workers can worsen provider/site throttling without improving useful throughput. For a repeatedly timing-out read surface, measure one bounded concurrency change and one duplicate-read reduction, then compare the remaining critical path with the existing client boundary. If the user-visible failure persists, reassess synchronous whole-result delivery before dispatching another optimization round; repeated component gains can leave the same broken screen. Trace existing saved projections and update workers before proposing prepared, scoped, or asynchronous reads. Present such a lifecycle change as a design requiring implementation and authorization-freshness tests; benchmark projections supply planning estimates, while the deployed browser establishes acceptance. For saved-result delays, measure provider execution, result commit, projection queue wait, readable-result projection and record postprocessing separately. When a matching saved result is already readable, let the UI display it while authorized postprocessing remains pending; retain exact job/version/result checks and verify that a slow record task leaves other completed results readable. Test missing and explicit-null retry timestamps separately in recovery queries, because database comparisons can exclude null rows.
7. **Compare complete costs.** For hosted-versus-self-hosted models, first establish checkpoint-specific CPU/GPU support, input limits and documented memory guidance. Mark smaller hosting tiers as experimental until measured; a CPU benchmark on a larger machine establishes no capacity guarantee for the cheaper tier. Evaluate the exact language and task on the same corpus before recommending substitution, and treat fine-tuning as conditional on that evaluation. Separate current fixed costs, proposed fixed increments and usage-dependent costs. Verify prices against the exact region, SKU, billing unit and tier; distinguish applicable free allowances from marginal paid rates. Include models/search/retries, state/storage requests, network/security, logs/retention, registry/build and recovery operations. Compare warm and low-duty-cycle workloads under explicit assumptions; a cost preference is not proof one host is always cheapest.
8. **Review uncertain boundaries, then implement vertical slices.** Begin with missing visibility on an existing execution, establish risky-runtime isolation, extend evidence/state, integrate suspend/resume and budgets, then exercise user flows and recovery. Test notification loss, empty results, dependency removal, authorized input revisions, expired leases and concurrent commits before accepting a happy-path resume. Follow `references/durable-observation-recovery.md` for the recovery and context-fencing recipe. Keep baseline checks, independent review, implemented behavior, real-surface verification and production rollout distinct.
9. **Close delivery through the deployed browser journey.** For launch work, include actual UI behavior and UX in the completion criteria. After deployment, use the designated account and Workspace to submit a natural question, observe progress, open the answer's cited original, ask a follow-up in the same conversation, and refresh/reopen. Exercise cancellation, failure/retry, mobile layout, and keyboard interaction within safe test boundaries. Fix observed defects and rerun the same journey on the changed revision; API success covers its own boundary while browser evidence establishes the user's completed task. Record frontend and backend revisions separately, then test immediate completion-to-detail navigation and saved-result reopening as distinct paths; mismatched deployments and missing version bindings can leave a completed server task inaccessible in the UI. Treat a completed scenario batch as a defect inventory until its required outcomes and blocking UI defects are resolved. When an existing scenario set is named, recover its original registry, exact prompts and UI actions before testing; preserve question-answering and judgment flows as separate acceptance groups and compare each case against its prior result.

## Standing expectations

- For question-answering products, make ordinary answers direct and natural: answer the question first, scale explanation to its difficulty, and add sources or next actions when the question needs them. Apply criteria, scores, options and judgment-report structure to explicit judgment or format requests. Check the actual transmitted prompt and deployed answer policy together, because a global evidence-policy instruction can override a conversational tone prompt. Evaluate ordinary answers and judgment flows separately; a GPT-style comparison requires observed reference outputs rather than an invented baseline.
- When repeated deployed reruns fail, replay the exact saved tool outputs through the default caller before paying for another question. Trace follow-up eligibility, remaining deadline, source selection and condition-recipe matching; adapter tests alone leave caller overrides and unselected URLs untested. Rerun only affected original cases after the demonstrated cause is fixed, and retain each failed attempt in the case history.
- Explain the existing-versus-added product delta before adding infrastructure vocabulary. This user expects placement, connections, complete cost and the behavior each addition enables.
- Rank quality work by observed user-facing defects and useful output. Keep security hardening and regression documentation explicitly categorized and scoped; a checklist preserves coverage, while changed and exercised behavior establishes a quality improvement. For competitor-inspired work, evaluate shared readability, progress, evidence, recovery and reliability separately from the product's distinctive judgment capability; judge the latter against user constraints, comparison consistency and actionable conclusions.
- Lead progress updates with the user flow that now works, its observed scope, and the next missing connection. Put test counts after that milestone; passing more component tests can leave the requested product flow disconnected. When the user asks whether work is running, establish current execution from the active child or process and its latest result; name a stopped run plainly and distinguish it from an active checklist item. Keep the reply short and identify the exact acceptance boundary still pending.
- Explain activation status by naming the exact capability and surface: for example, whether a user question can launch a server browser, apply requested site conditions, and reopen the saved evidence. State whether the result used controlled fixtures, an actual external site, or the deployed product; bare labels such as disabled, offline, or HOLD leave the user unable to judge progress.
- Keep the next completion gate tied to the requested user outcome. For a launch request, separate launch-critical authority, real execution, saved evidence, and failure cleanup from follow-up quality comparisons and feature expansion. Use the same product implementation and answer-affecting configuration in local validation and production delivery; isolate QA accounts and data while keeping runtime composition equivalent. Compare the deployed code revision, model/effort settings, source coverage and feature flags with the validated path, because environment-specific behavior can change answer quality. Carry a concrete implementation path to the production runtime; treating a QA-only adapter as the delivery endpoint postpones the requested product. When the user approves a blocked recovery, execute that scoped recovery alongside independent delivery work instead of silently shelving it. After a connected fixture flow passes, explicitly track replacing its external boundaries and qualifying the real host rather than presenting repeated component reviews as end-to-end completion. After host qualification passes, inspect the actual composition-root construction, injected transport/contract and worker selection before claiming the product can use it; an operator-run authenticated canary can succeed while the application's default dispatcher remains unset. Carry the same authorized question through evidence publication, resume, citation, saved answer and original reopening before promoting the full-flow claim.
- Treat willingness to rebuild as permission to reconsider assumptions, not a requirement to discard working components. Justify replacement with measured limits or unmet contracts.
- For connected-knowledge assistants, preserve discovery of useful information the user has not named and may not know exists across authorized mail, documents, and databases. Review the sequence candidate discovery -> selective original/value reading -> grounded answer; evaluate missed useful sources alongside irrelevant personalization, because a question-only source-type gate can hide the product's distinctive value.
- For knowledge-generation changes, establish information-unit selection before designing extraction or progress displays. Separate existing-knowledge retrieval, new accumulation, judgment-record preservation/reuse, and ontology extension. Evaluate mixed inputs in their full context, preserving useful goals, constraints and actual changes alongside routine questions. Keep fidelity, future reference value, attribution and purpose/time scope as separate decisions; relation counts describe processing while retained meaning establishes usefulness. Reuse an existing semantic call where suitable, and state whether selection actually happens before extraction or only before materialization. Track connector, ordinary-chat, judgment and correction producers individually so a connected first slice has a clear remaining scope. Follow the generation and admission recipe in `references/connected-knowledge-discovery.md`.
- For personal knowledge maps, automate connection maintenance and updates, and offer optional inspection, correction and addition. Present how the system understands the user with source-backed relationships and ensure user corrections reach subsequent answers or judgments; keep routine relationship auditing with the system. Establish the approved product purpose from the user's explicit decision, and use recordings or research as supporting interpretation with their actual authority.
- Before changing shared assessment checks or policy versions, inspect persisted validators, integrity hashes, evaluation fingerprints and recovery-version branches together. Bind new selection results to the exact source revision and request, preserve historical reads under an explicit compatibility rule, and keep semantic-policy evolution separate from format-only recovery authorization. Test exclusion as well as retention through worker, storage and map/read consumers; assert completed replay produces no additional provider call. Separate protocol-double success, real-model classification accuracy, independent user QA and production behavior in progress reports.
- Keep narrowly scoped classifiers/judges in their stated role. Trace the current evaluator's actual inputs and consumer before recommending an extension; passage-type classification, question relevance, and source existence are separate tasks. Treat candidate-aware relevance assessment as an experiment with an abstention path, compare it with existing search reranking, and verify the data-transmission scope before sending private candidates to another provider. Read `references/connected-knowledge-discovery.md` for the coverage audit and comparison recipe.
- Separate durable accounting and unsampled aggregate counters from sampled diagnostic traces. Preserve interrupted or unreported usage as unknown, not zero cost. State the ledger's checkpoint, late-update and resource coverage bounds; a durable invocation row does not establish complete question cost.
- Keep already-completed replay and genuine no-op work free of accounting writes, while requiring synchronous accounting admission before eligible paid work. Determine eligibility from current saved state rather than incoming status, because stale pending input can refer to a completed execution.
- Treat accounting admission failure and final-record failure separately: block a new transport when its mandatory start cannot be saved, but preserve a known provider result when only final recording fails. Verify both at the connected caller before claiming recovery.
- Distinguish local capacity, external quota, site restrictions, network delay and correctness failures. Preserve uncertainty instead of forcing every slowdown into one cause.
- Capture actual platform readback before encoding a runtime security predicate or its test fixture. CLI serialization, unordered state sets and inherited process flags can differ from launch arguments while preserving the intended control. Reproduce the observed refusal at the real validator, retain adversarial cases, and verify the corrected boundary on the host. Use the representation-safe readback procedure in `references/measurement-and-capacity.md`.
- Establish browser process/credential/egress isolation before accepting a host. Keep offline regressions, applied configuration, observed runtime controls and full acceptance separate. Pair blocked connections with live positive controls or matching enforcement counters; require continuous traffic probes for claims about safe policy replacement. Preserve unknown native-probe gates while recording additional host evidence separately. Follow the Linux VM recipe in `references/measurement-and-capacity.md` for atomic firewall replacement and fresh identity evidence.
- Qualify a hosting candidate on the actual cloud platform in an isolated non-production resource group, not on the developer machine or a local VM. Kernel/seccomp support, sandbox enforcement, managed-identity exposure, egress controls and inter-service latency are host properties, so local results do not transfer. Do not propose local runtime installation as the next step for host qualification. Once the user approves cost and scope, follow the cloud qualification recipe in `references/measurement-and-capacity.md`.
- Size from observed arrival rates, slot occupancy, throughput, tail latency and dependency headroom. User counts and example slot calculations are assumptions, not demonstrated capacity.
- Define network acceptance by permitted communication paths, including trusted DNS forwarding, before integrating external-site execution. Packet captures and positive/negative controls establish the observed path; destination-IP blocking alone leaves hostname and resolver permissions unspecified.
- Name the deployed owner of each enforcement and cleanup step. Keep parent-operated trial controls separate from frozen runtime guarantees, and require supervised cleanup/recovery evidence before promoting them to unattended execution; a successful parent finally block covers only that trial.
- Treat a selected prewarm design as a lifecycle change requiring fresh qualification: define prepared-slot ownership, network-denied readiness, credential-proof freshness, single-job data isolation, bounded idle lifetime and supervised cleanup before enabling observation. Trace the expensive process startup to its actual call site and place it before admission; a prepared container whose browser starts inside the grant window still consumes that window's startup budget. Preserve the existing backend contract when that is the selected goal; distinguish offline adapter tests from actual readiness evidence.
- Verify parallel receiver and lifecycle implementations both together and through an explicit adapter. Define context-manager ownership, result mapping, generation mapping and UTC-to-monotonic deadline conversion before claiming integration; separately passing module suites can conceal incompatible interfaces.
- When a host engine waits on a real pipe/socket but takes its deadline from an injected System clock, convert the remaining budget to a real monotonic wall deadline exactly once at entry and bound each `select` by both clocks. A fake clock that never advances turns a `select` retry loop into an infinite hang under test while production looks fine.
- Before typing a recipe/condition schema for a site observer, read the product tool contract: browser condition values arrive as name/value strings (`{'people': '4'}`), so an `int` field must accept one canonical decimal string and compare applied DOM strings against the request; JSON ints in the recipe break the existing backend contract.
- Test a stdio child protocol with the real child code running in a thread over `os.pipe` descriptors behind a fake Popen; construct the fake streams with the exact `bufsize` passed by production and assert argv/env/stderr settings. A raw-stream fake can conceal buffered read-ahead and blocking writes in production. Exercise held partial headers, held partial payloads, full write pipes and unreaped termination with finite watchdogs, then run a real local subprocess probe. Bound raw-fd reads and writes by the deadline and clean up the child on every exit path. State the child, browser and host substitutions explicitly; docker exec, Chromium and kernel readback stay host-qualification gates.
- Report interpreter compatibility separately for the host controller and container observer. Resolve each interpreter from its actual command and image base; require execution with the target interpreter before claiming runtime compatibility. For an isolated container command, add image-build checks under the workload user with that exact executable and `-I`, checking the pinned browser-library version and browser assets. Syntax parsing and a root import with a different invocation cover only their stated checks.
- Separate execution expiry, replay protection and retained-data deletion. A deadline grace authorizes only the specified terminal state transition; establish an explicit retention policy before pruning replay rows, evidence or job documents.
- Distinguish replay refusal from tombstone-capacity exhaustion with a typed outcome or exception; preserve retained rows and report capacity without inventing automatic cleanup.
- Derive durable-completion lock waits from the original caller/lease budget, recheck after acquiring the lock and after COMMIT, and require exactly one matching completion transition before signing success. Document that synchronous SQLite/fsync calls cannot be hard-cancelled by a deadline check.
- Keep secure-file inspection read-only and separate from one-time creation. Compare pathname and descriptor identities, allow an optional rollback journal to disappear without recreation, and surface post-COMMIT inspection failures as typed committed uncertainty that blocks retries.
- Keep each job's supervisor generation, trusted host-address binding and admission evidence immutable through cleanup. Test successful external work and natural expiry together, then independent caller loss, forced termination and competing generations; separate execution outcome from cleanup outcome and retain unknown historical failure causes. Follow the supervised-controller recipe in `references/measurement-and-capacity.md` for Linux rule readback, residual-socket admission, lifecycle commands and recovery bounds.
- Validate result fields against the actual probe schema before assertions. Persist successful runtime output and a separate parent-harness failure record when a nonexistent result key interrupts the trial; stop the exact started instance and remove/read back temporary site access in finally.
- Keep reloadable qualification helpers and phase records in approved scratch/evidence paths for long tool runs. Keep credentials and full control-plane bodies out of helpers and reports, and reacquire fresh identity proof in memory before the next admitted execution.
- Preserve condition-verification requirements when connecting a real observer. Treat unapplied conditions, blocked navigation and timeouts as explicit unverified results; admitting unconditional page text as conditional evidence would silently change the user's requested answer. Classify failures by execution stage as well as exception type: after entering external work, keep unresolved controller or engine failures unknown and deadline failures timed out; reserve unapplied for explicit condition or completed-body admission failure. Broad ValueError catches can also include ownership and deadline exceptions raised after observation. Follow the stage-sensitive classification checks in `references/durable-observation-recovery.md`.
- Separate host-result authentication from observation correctness. A valid signature establishes provenance and request binding; verify applied conditions and evidence contents independently before citation admission.
- Inventory every live-harness supplement before promoting a connected-flow result: injected condition capabilities, refreshed bootstrap identity evidence, alternate conversation creation, and manual control-plane delivery each identify a product dependency to trace. Connect each required dependency to its deployed producer and default consumer, then rerun with that supplement removed; a successful supplemented trial proves the trial's observed scope.
- Trace bootstrap-start evidence and observation-phase proof separately through their readers, schemas, refresh owners, and consumption rules. Supply both from the trusted control plane when both are required; a fresh projected snapshot can coexist with a missing full identity or image-pull binding consumed at each slot start. Exercise the collector's exact serialized envelope through the installed bootstrap validator before enabling its recurring loop, because successful delivery and generation minting can coexist with every slot preparation failing. Preserve the actual collection provenance through each adapter; REST evidence must retain its REST origin and pass an explicitly supported validator.
- Trace each per-slot trust artifact through its deployed owners: credentialed collector with exact target binding and bounded refresh -> root inbox -> root minter using the proof checker's validation -> durable minted/consumed state -> serving process. Identify the collector's actual hosting, authentication renewal, delivery route, and restart owner; a workstation Azure session covers a supervised trial, while production acceptance requires those dependencies to survive the operator going offline. Exercise two consecutive user jobs with automatic refresh and a stale-proof case that stays safely pending, because a one-job trial hides a missing generation owner. Obtain fresh identity evidence from the trusted control plane and preserve it through cleanup.
- Probe authenticated host readiness before claiming a job so known idle/busy states leave its attempt count unchanged. Test the race where the slot becomes busy after the probe separately: release the claim and use a bounded deferred retry only when the signed response proves observation never began; record any attempt consumed by that claim. Preserve post-send EOF/timeout as `unknown` and block automatic re-observation, because transport loss leaves execution ambiguous. Assert pending status, lease release, retry timing, attempt counts, and observation counts in both cases.
- Bound handshake work with a small semaphore of peer threads and the configured io timeout; a single-threaded accept loop lets never-handshaking peers serialize in front of the real worker and burn the prepared slot.
- Exercise the installed service entry with its exact interpreter, isolated flags, cleared environment, argv, ownership, and module layout before host qualification; pytest's import path can hide a service-start failure. When using a sibling-directory import guard, validate the resolved directory and modules before adding that directory to sys.path. Run a real subprocess for ExecStart and the recovery entry, then verify startup recovery, stop during observation, forced termination, and restart against durable cleanup/generation state; parsing unit argv alone covers only argument compatibility.
- State measured results and remaining gaps plainly. Design approval and green existing tests do not establish that the new user flow works. Verify child-reported file hashes and run the connected acceptance tests yourself before advancing the implementation claim; report full-suite failures with their actual identities rather than assuming equal counts prove identical failures. Read the test runner's own exit status and summary when a background shell reports success, because a trailing output command can mask a failed suite; retain skipped and expected-failure counts alongside passes.
- Qualify unattended collectors from the deployed worker entrypoint through lifecycle registration, exact host-key matching, credential retrieval, delivery and slot preparation. Use the cloud-worker connection recipe in `references/measurement-and-capacity.md`; hooks attached to a different application object leave the deployed worker without a collector.

## Deliverable

Provide a capability/resource delta table, execution/trust map, measurement/diagnosis plan, complete cost model, and ordered implementation gates with acceptance tests. Lead with meaningful product changes and demonstrated gaps. Link raw measurements rather than copying them into the report.
