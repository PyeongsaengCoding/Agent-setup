# Media production orchestration

## Procedure

1. Read project production contracts and latest user corrections. Separate deliverables, production start time, publication time, and platform-native scheduling. Before paid generation or full rendering, verify both exact-product facts and the commercial/reference-use rights of the planned assets; late rights discovery can leave finished videos unusable for the requested publication. Open the exact product's detail and alternate-view images at readable size before locking the script: count visible layers and filling zones, distinguish one unit from stacked halves, and check surface texture, cross-section and preparation state. Compare each generated candidate against those observations before consuming the remaining generation allowance or rendering the full timeline; text-only generation can preserve the food category while changing the linked product's structure or implying cooked surfaces and melted fillings. Keep observation-only product references separate from assets permitted in the delivered video or provider upload. If rights evidence is missing, inspect authorized alternatives before spending on the affected item and continue independently ready items. For a batch requested now, begin permitted artifact production immediately and retain only schedules still requested.
2. Carry delegated choices into execution instructions. For this user's shopping-shorts project, apply the standing delegation to choose recommended hooks, voices, scripts and final cuts and perform voice/editorial reviews internally; record the user delegation and actual artifact checks instead of waiting for routine approvals or inventing user approval. Keep publication within the already requested product/account/time scope and preserve new-payment, subscription, PAYG, optional paid-video and public deletion/replacement boundaries. Read the project's current delegation contract before execution and update existing timed jobs to use the same review owner. Verify the official supported model ID at production time when a current model is requested; record the model actually used.
3. Preserve the selected provider, model, account, and existing usage allowance. Respect requests to omit extra account-setting inspections and keep operations within approved spending scope. Ask only for choices that change that scope.
4. Discover authorized generation paths before declaring a missing capability. A missing tool name establishes that interface's absence; inspect equivalent authorized paths while preserving account and payment boundaries. Choose the least costly technique that delivers the requested visual event: use local animation for camera motion over existing images and reserve paid generation for new motion or viewpoints that the available assets cannot express. For reference-led remakes, follow [reference-led motion design](references/reference-led-motion.md).
5. Dispatch self-contained instructions with current choices and exclusions. For this user's shopping-short motion production, assign authoring and rendering to Claude; retain parent ownership of deliverable verification and delivery. When the user requests Fable followed by Opus on exhaustion, start with Fable and switch to Opus only after an observed quota or availability failure, preserving completed assets and the production checkpoint to prevent duplicate generation charges. Report the observed execution model separately from the selected route. Track child IDs separately from batch IDs and steer using the child ID. When steering fails, report adoption by the current run as unverified; saved future instructions establish future behavior only.
6. For schedule cancellation, list jobs, remove the exact matching job, and list again. Check artifacts and existing running work before replacement production to prevent duplicate charges. Keep late results from removed schedules separate from active replacement work. For scheduled publication, inspect both the scheduler and platform-native publication records before reporting an existing reservation. Resolve relative dates to an exact local date and timezone, and distinguish proposed times from registered jobs. During a cadence change, separate the effective date of new production from publication of the already prepared batch; preserve that batch's accepted files and slot mapping so a scheduling correction does not trigger duplicate generation. Carry the user's accepted product-to-slot assignments into preparation and publication; apply a meal-time food preference to the requested batch while retaining the other accepted products. Verify each product's platform-specific affiliate links and landing pages before stating that links are ready; a completed MP4 establishes production readiness only.
   - When registering a publication trigger before production finishes, persist the exact product, target time, planned package path, and pending review states. Make the job read the actual package, delivered file hash, review evidence, and the applicable user authorization or standing delegation before publication; a planned path establishes only a future artifact location. With creative review delegated, use actual agent review evidence and the delegation reference rather than reintroducing a user-approval wait. Carry the latest batch-scoped publication exception into unattended execution alongside factual checks, asset-permission evidence and account checks, so an older manifest or job prompt cannot recreate a wait the user explicitly removed.
   - List jobs before creation to prevent duplicate registrations, then read back the exact new jobs and their next-run timestamps. Preserve unrelated existing jobs. Report timed execution registration, platform-native upload scheduling, and verified public posts as separate milestones, because each has a different completion condition.
   - Inspect the returned delivery destination when registering jobs. If output is local-only, name where results will be recorded; claim a chat notification only after a delivery channel is configured and verified. Prepare approved uploads and available native schedules ahead of the target time, because starting a browser upload at the target consumes the publication window.
7. Verify actual deliverable files and acceptance criteria before completion claims. Read child packages and review evidence yourself, hash the delivered files, and compare representative full-size frames with the exact product sources. Treat required checks listed as `not_observed` as pending even when the child reports `passed`, no blockers, or `publication_ready: true`; STT supports transcript checks, frame sheets support sampled visual checks, and full listening/realtime playback require their own observed evidence. When parent review finds a defect, set the affected package and every corresponding per-item and batch readiness field to pending, retain passing technical evidence, and reconcile publication intent, current-state summaries and scheduled job instructions before handing off a correction. Name the defect and required replacement evidence, preserve the previous version, and re-review the corrected hash before releasing publication. Audit paid calls against the selected scene technique and spending scope: a successful export can still contain an unnecessary paid camera-motion call. Record violations and actual or estimated usage explicitly, and carry a local-only generation gate into the next handoff when local animation expresses the whole scene. Distinguish dispatch accepted, assets generated, export completed, and artifact verified. Read substantive scheduler output because a successful scheduler exit can contain an interrupted production report. Before promising a recurring end-to-end operation, exercise the required review method and the production-to-publication handoff on actual artifacts. Keep a capability gap explicit and resolve it before the publication window; continuing to repeat technical checks leaves the missing review unresolved. Apply scoped user exceptions to publication authorization while preserving the unverified review facts, and keep future batches under their own review requirements.
   - When a video attachment cannot expose sound to the reviewer, test a full-length audio-only stream-copy from the same artifact before concluding that all attachment paths fail. Verify identical extracted audio-stream hashes, withhold the script during the capability probe, and require acoustic observations beyond transcript or numerical waveform analysis. Keep model identity unverified when the web UI does not expose it. First-use provider consent and account onboarding remain explicit boundaries; record and stop at those gates instead of silently enabling a new service.
8. Keep verification proportional. Check feature labels and buying information against both viewport bounds and platform-safe vertical regions after layout fixes; moving a clipped label to the lower edge can trade horizontal clipping for platform-UI occlusion. Verify the changed scene and all distinct captions rather than inferring full-layout safety from caption-only tests. Obtain permission before installing substantial optional verification dependencies. When the user removes a verification step, steer active workers to stop it, remove authorized installations and assets, verify removal, and continue the remaining deliverable work.
9. Treat an accepted current version and feedback for the next version as separate scopes. Publish the accepted file unchanged when requested; apply the requested creative improvement to later production. For this user's shopping shorts, verify the channel's designated browser profile and the actual YouTube channel plus Threads, TikTok, and Instagram accounts before posting. An explicit four-platform instruction limits publication to those four destinations. Carry the approved version, product, links, disclosures, and publication intent into the publishing handoff. When the user requests direct publication at a particular time, preserve that execution mode and distinguish a timed agent trigger from platform-native scheduled posting. Confirm the exact local date and an observed execution mechanism before promising unattended publication; a proposed timetable establishes only intended times. Verify each resulting post at its unique URL before reporting success.

## Shopping-shorts product discovery

1. Resolve product discovery against the project's current selection contract before sourcing assets. For this user, inspect other shopping creators' recent public Shorts and Reels for candidate discovery; use the channel's own results for post-publication learning. Record source URLs, observation time, publication date, views, views per elapsed day, like rate, comment rate, and purchase-intent comment examples. Keep bundle-video engagement at source level to preserve correct product attribution.
2. Cross-check candidate demand with Naver DataLab Shopping Insight's recent daily popular search terms and changes across dates. Record the observed period and filters. Keep search interest, short-video response, and exact-product purchase availability as distinct evidence; a monthly top list or high sales signal alone leaves the requested recent-video investigation incomplete.
3. Search across everyday life: food and drinks, kitchen, cleaning, storage, bathroom, vehicles, digital products, fashion and beauty, parenting, pets, hobbies, fitness, and outdoor activities. Rank by observed demand and persuasive visual potential. Avoid narrowing '생활템' to household utilities or imposing equal category quotas; reusing prepared food assets can otherwise dictate the selection before research.
4. Match each candidate to the exact currently purchasable product and compare existing production and publication records before commissioning it. Exclude the same product under a changed name or pack quantity; allow an explicit user-requested remake within its stated scope. Present source metrics, recommendation reasons, and trade-offs separately rather than inventing a blended score.
5. Preserve the accepted batch when the user asks to broaden future discovery. Steer research toward the new scope while keeping existing approved exports and publication choices intact; future-selection feedback alone does not authorize replacing completed items.

## Shopping-shorts creative direction

- For this user's dynamic shopping shorts, design a persuasive product advertisement: a concrete buying situation, desire-led opening, product reveal, visible differentiator, usage context, purchase reason, and CTA. Give every scene new persuasive information; connect cut rhythm, typography, transitions, and sound to that information. Evaluate zooms and parallax by their contribution to purchase desire.
- Explain proposed creative changes with an actual scene-by-scene example and sample dialogue, specifying what each shot persuades the viewer to understand or want. When the user asks for marketing-style motion, specify the opening promise, product entrance, differentiator reveal, usage payoff, and final product/CTA composition before naming animation effects; this makes the selling argument concrete.
- Treat a motion-ad request during an active production as a creative revision to the same deliverable. Steer the existing child with the updated storyboard and acceptance criteria while preserving the product, spending scope, and publication boundary; this prevents duplicate work and charges. Report queued steering as delivered instructions until the child confirms adoption.
- For a request to make tomorrow's first short, produce one reviewable MP4 now. After the user accepts that first short and says to continue an established daily batch, produce the remaining batch items while preserving the accepted file. Publish or schedule only within an explicit publication instruction.
- Build the graphic palette around the product's own colors. For this user's product-detail emphasis, retain circles when they clearly identify the feature and use a warm ivory or another warm, product-compatible color with visible contrast. Reserve yellow for accepted subtitle emphasis; avoid yellow rings painted over the product because they read as diagrammatic and compete with food texture. Apply color corrections to the specified element rather than removing all yellow or replacing every circle with a pointer.
- Keep feature highlights visible through the relevant narration and long enough to locate the detail and read its label. Separate entrance, readable hold, and exit; inspect real-time playback at phone scale before accepting the timing, because a contact sheet cannot reveal an effect that disappears before recognition.
- For color feedback, inspect the actual relevant frames before answering. State which element draws attention, how it interacts with the product and background, and the concrete replacement you recommend. Distinguish visual feedback from permission to revise an accepted file.

## Reporting

- Lead with verified artifacts or the exact unfinished stage.
- Describe production activity as current only when observed; a dispatch acknowledgment supports 'dispatched'. For a direct progress question, check live child status and answer briefly with the observed stage and whether an MP4 exists. A running child establishes active work; identify rendering or validation as the current stage only with evidence for that stage.
- Report useful artifact milestones; keep dependency downloads and harmless shell warnings in technical evidence unless they block production.
- Preserve original assets and existing publications during retries and replacements.
- Separate publication authorization, asset-permission evidence, technical review, and actual public visibility in records and reports. Keep asset permission recorded as unverified until supporting evidence is obtained. When the user explicitly directs publication of an existing batch while skipping its permission-verification wait, record that direction as a batch-scoped publication exception and reconcile the affected packages, publication intent, current-state summary, and existing timed jobs before reporting the wait removed. Preserve the remaining account, product-fact, disclosure, file-hash, spending, and duplicate-post checks. Assign readiness from those remaining conditions and the explicit exception; retain any unperformed playback or listening checks as unverified. An exception authorizes the stated operation and leaves the third-party permission evidence unchanged. Apply it to future batches only when the user expressly gives that broader scope.
- Handle intermediate child-process notices internally unless they expose a blocker or a useful artifact milestone. Consolidate render, validation and scheduling updates into a short report instead of sending one progress message per process completion.

## Claude execution boundary

- A delegated Claude child (subagent) satisfies Claude ownership of motion authoring. Verify the observed child model at dispatch and completion before claiming Claude ownership; a selected route can execute on a fallback model. When the user requires Claude with Fable-to-Opus fallback, keep motion authoring within those approved models and stop or repair the route if another family is selected. Generic instructions to continue production preserve the named-model boundary. Invoke a separate Claude CLI only when its capabilities are needed; preserve each executor's own routing settings. When a subprocess exits unsuccessfully, inspect its actual error before attributing the failure to model quota or shell startup warnings.

## Boundaries

Project contracts own product facts, rights, accounts, subtitles, and publishing requirements. Runtime tools own scheduling and delegation behavior; consult current schemas for parameter names.
