# 한국어 문장 다듬기

## 범위

- 진단 요청: 문제 문장, 유형, 이유를 목록으로 돌려준다. 원문은 고치지 않는다.
- 수정 요청: 필요한 부분만 고친 수정본과 주요 변경 이유를 돌려준다.
- 사실·고유명사·수치·날짜·인용·URL·코드·명령어는 바꾸지 않는다. 글쓴이의 말투(반말·존댓말, 격식)와 문서 장르를 유지한다.
- 같은 글에 영문 구간이 있으면 그 구간은 humanizer 기준으로 따로 본다.

## 고객에게 보내는 개발·호환성 안내

- 기존 메일이나 통화가 근거로 지정되면 그 내용을 먼저 읽고, 실제 전사 결과를 확보한 통화만 발언 근거로 사용한다. 이전 메일의 호칭과 문맥을 이어 쓴다.
- 고객용 후속 메일은 요청에 따라 무엇을 바꿨는지, 기존 자료를 새 입력에 어떻게 연결했는지, 실제 확인한 범위와 남은 항목을 짧은 문단으로 설명한다. 내부 점검 보고서의 파일 개수·시험 수·구현 용어는 독자의 판단에 필요한 것만 남긴다.
- 호환성 설명에는 비교한 두 출처와 연결 기준을 밝힌다. 기존 입력에서 옮긴 검사본을 썼다면 그 사실을 짧게 쓰고, 양식 대응·파일 접수·실제 값 비교의 결과를 각각 정확히 표현한다.
- 개발 환경에서 확인한 내용은 개발 환경 결과로 쓰고, 운영 반영은 확인된 변경만 안내한다. 일부 대상·항목의 일치 결과에는 적용 대상과 항목을 붙여 전체 호환성이나 전체 정확도로 확대하지 않는다.
- 간단한 메일을 요청하면 바로 사용할 초안을 먼저 제시한다. 회의 회신은 인사, 날짜·장소 확인, 현재 진행 상황 1~2문장, 서명으로 마친다. 상세 표·검사 수치·별도 해설은 독자가 요청한 경우에 붙인다.
- 회의 일정 회신에는 "○월 ○일 ○시 ○○에서 뵙겠습니다"처럼 자연스러운 표현을 쓴다. 식사 등 부수 일정은 사용자가 회신에 포함해 달라고 할 때만 적는다.
- 현재 진행 상황은 목적부터 설명하고 방법을 짧게 잇는다. 예: "기존 자료를 새 양식에서도 활용할 수 있는지 확인하기 위해 기존 입력을 새 양식으로 변환해 비교하고 있습니다." "처리·연결" 같은 내부 동작의 나열은 독자가 이해할 업무 표현으로 바꾼다.
- 이전 안내에서 이미 전달한 운영 반영은 생략하거나 이전 완료 사실로 표현해, 과거 완료와 현재 진행 중인 검사를 구분한다.
- 회의에서 결과를 발표하거나 적용 범위를 협의한다는 문장은 사용자가 그 안건을 승인한 경우에 쓴다. 현재 상황만 요청하면 현황 설명에서 마친다.
- 사용자가 특정 문장·호칭·길이를 수정하면 해당 부분과 문맥에 필요한 최소 범위만 고친 최종 초안을 제시한다. 삭제한 내용은 다음 수정본에서도 제외한다.

## 고객 질문에 대비한 변환 방법 설명

1. 사용자에게 보낸 문구와 질문받을 주제를 먼저 확인한다. 짧은 고객 회신과 사용자를 위한 상세 기술 설명의 분량을 각각 맞춘다.
2. 작업 보고서로 실행 범위를 확인한 뒤 실제 변환 코드와 그 코드가 호출하는 원본 파서를 읽는다. 파서가 읽은 항목과 변환기가 출력한 항목을 따로 대조해, 추출 가능한 값 전체를 지원 범위로 설명하는 일을 막는다.
3. 원본 입력 → 중간 집계 → 새 양식 필드의 순서로 설명한다. 행 분할·그룹화·합산 위치·날짜 의미·생성한 내부 번호와 공란 유지 기준을 명시하고, 변환에 쓴 가정은 먼저 밝힌다.
4. 입력 원본과 비교 원본의 독립성, 별도 검사본 생성과 원본 보존을 설명한다. 형식 변환, 접수·조회, 실제 값 비교의 확인 범위를 각각 적는다.
5. 실제로 옮긴 항목과 추가 대응할 항목을 구분하고, 끝에 회의에서 말할 수 있는 짧은 답변을 붙인다. 상세 근거는 코드 위치로 연결하고 고객 식별정보·원문 데이터는 예시에 복사하지 않는다.

## 찾을 패턴

| 유형 | 예 | 고치는 방향 |
|---|---|---|
| 번역투 어순·조사 | "~에 대해 논의를 진행했다", "~을 통해 ~을 할 수 있다", "~에 있어서" | 동사로 직접: "논의했다", "~으로 ~한다" |
| 과도한 명사화 | "확인 작업을 수행하였다", "개선이 이루어졌다" | "확인했다", "개선했다" |
| 부정·대조 틀 | "단순히 X가 아니라 Y다", "X라기보다는 Y" | 말하려는 Y를 바로 쓴다 |
| 상투적 도입·결론 | "오늘날 빠르게 변화하는 ~에서", "결론적으로", "이를 통해 ~할 수 있을 것입니다" | 삭제하거나 구체적 사실로 바꾼다 |
| 부풀린 수식 | "매우 중요한", "혁신적인", "획기적으로", "다양한" | 근거가 있는 구체 표현이나 수치로 바꾸거나 삭제 |
| 반복 종결 | 문장마다 "~합니다", "~입니다", "~할 수 있습니다" | 문장 길이와 종결을 섞고, 가능성 표현은 사실이면 단정 |
| 기계적 나열 | "첫째, 둘째, 셋째", 모든 문단이 같은 구조 | 내용에 맞게 문단을 합치거나 목록으로 |
| 불필요한 영어 | "인사이트를 리뷰하고 액션 아이템을 디벨롭" | 통용되는 한국어로. 고유명사·코드·업계 표준 용어는 유지 |
| 빈 강조·면책 | "참고로", "물론", "중요한 점은", 요청하지 않은 주의 문구 | 삭제 |
| 이중 피동 | "되어지다", "보여지다" | "되다", "보이다" |

## 순서

1. 독자와 목적(보고, 안내, 기술 문서, 대화)을 정한다. 보고서 문체처럼 프로젝트가 정한 기준이 있으면 그 기준을 먼저 따른다.
2. 위 패턴을 문단 단위로 찾는다. 같은 문제가 반복되면 대표 예와 개수로 묶는다.
3. 수정 요청이면 고친 뒤 원문과 비교해 사실·수치·고유명사가 그대로인지 확인한다.
4. 고칠 것이 없으면 그렇다고 짧게 답한다. 고칠 거리를 만들어 내지 않는다.
